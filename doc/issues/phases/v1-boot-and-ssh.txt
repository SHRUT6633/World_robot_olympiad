history repo (v1.0 -> v9.9).  Every entry includes WHAT HAPPENED,
WHY IT HAPPENED (root cause / deep research), the terminal type and
exact output, and the FIX with how many days it took.

E0001 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : ModuleNotFoundError: No module named 'sensors'
Terminal  : Pi SSH terminal
  $ python3 main.py
  Traceback (most recent call last):
    File "main.py", line 6, in <module>
      from sensors.camera import PiCamera
  ModuleNotFoundError: No module named 'sensors'
WHAT HAPPENED
  The very first morning run of v1.x died at the first import, before a single line of robot code could execute. The whole skeleton was there, but Python refused to see it.
WHY IT HAPPENED (root cause)
  Python resolves packages through sys.path, and sys.path[0] is the directory of the script being run, not the current working directory. The sensors package lived under pi/, so launching from the repo root made it invisible. ModuleNotFoundError is raised at import time, which means everything after the import line is unreachable - no logs, no GPIO init, nothing.
FIX (took 1 day)
  Fixed by running the script from inside pi/, and later made permanent with sys.path.insert(0, os.path.dirname(__file__)) so the package resolves no matter where the script is launched from.

E0002 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : ImportError: cannot import name 'PiCamera'
Terminal  : Pi SSH terminal
  $ python3 main.py
  Traceback (most recent call last):
    File "main.py", line 3, in <module>
      from picamera2 import PiCamera
  ImportError: cannot import name 'PiCamera' from 'picamera2'
WHAT HAPPENED
  The first camera test failed at import. The library was installed, so the surprise was that the symbol itself was missing.
WHY IT HAPPENED (root cause)
  picamera2 exports the class Picamera2 with a capital P. Python names are case-sensitive, and unlike C there is no link-time check - the failure only appears when the module is actually imported on the Pi. It never shows on the PC because the package does not exist there at all, which is exactly why this slipped past the laptop tests.
FIX (took 1 day)
  Fixed by using the exact class name Picamera2 and adding a startup import check so the mistake fails loudly and early instead of silently.

E0003 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : IndentationError: unexpected indent
Terminal  : Pi SSH terminal
  $ python3 main.py
    File "main.py", line 12
      print('i2c ok')
  IndentationError: unexpected indent
WHAT HAPPENED
  The morning's edits crashed the script before it even started. A block that looked right in the editor was illegal to the interpreter.
WHY IT HAPPENED (root cause)
  The file mixed tab characters with spaces. Python 3 forbids mixing them for indentation because they are ambiguous - one tab can be 4, 8 or 12 columns depending on the editor. The parser rejects the file during compilation, so no code runs at all; the error appears the instant the script is launched.
FIX (took 1 day)
  Fixed by reformatting the block with spaces only, then setting the editor to convert tabs to 4 spaces so it can never come back.

E0004 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : TypeError: unsupported operand type(s) for +: 'int' and 'str'
Terminal  : Pi SSH terminal
  $ python3 main.py
    File "main.py", line 18, in <module>
      dev = bus.read_byte_data(addr, reg) + 'x'
  TypeError: unsupported operand type(s) for +: 'int' and 'str'
WHAT HAPPENED
  The I2C scan report crashed halfway through building its output line. It had worked yesterday on the happy path, so the bug only appeared on a specific address.
WHY IT HAPPENED (root cause)
  read_byte_data returns an int, and the code appended the string 'x' to it. Python is dynamically typed, so the mismatch is only detected at runtime - the line only executed for addresses that returned a value, which is why the earlier test addresses passed silently. This is a classic type-contract bug that static analyzers catch immediately.
FIX (took 1 day)
  Fixed with str() wrapping and a review rule: every format that mixes types goes through f-strings, where the conversion is explicit.

E0005 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : NameError: name 'smbus' is not defined
Terminal  : Pi SSH terminal
  $ python3 main.py
    File "main.py", line 9, in <module>
      bus = smbus.SMBus(1)
  NameError: name 'smbus' is not defined
WHAT HAPPENED
  The I2C bus scan died at the first bus access. The import line at the top of the file was there, so the name should have existed.
WHY IT HAPPENED (root cause)
  The import statement import smbus2 was present, but the code referenced smbus. The alias was never created because the import was never written - the file used the raw package name in one place and the alias in another. NameError surfaces lazily at the first use of the name, not at import time, so the file parsed fine and only exploded mid-run.
FIX (took 1 day)
  Fixed by importing smbus2 as smbus and running a quick grep for every usage to confirm no other raw references remained.

E0006 | v1.0 | SMALL | Found Day 1 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : FileNotFoundError: [Errno 2] No such file or directory: 'config.json'
Terminal  : Pi SSH terminal
  $ python3 main.py
    File "main.py", line 22, in <module>
      with open('config.json') as f:
  FileNotFoundError: [Errno 2] No such file or directory: 'config.json'
WHAT HAPPENED
  The script died while reading its configuration. It worked in the repository, so the missing file only appeared once the code was deployed to the robot.
WHY IT HAPPENED (root cause)
  The config file was never copied to the Pi - only the code folder was synced. Worse, the path was relative, so the file location depended on the working directory at launch; systemd and cron would look in entirely different places. The error is raised by the open() syscall when the kernel returns ENOENT, and nothing in the code anticipated it.
FIX (took 1 day)
  Fixed by scp'ing the config, switching to an absolute path built from the script location, and adding an explicit existence check with a clear message at boot.

Error     : SyntaxError: invalid syntax
Terminal  : Pi SSH terminal
  $ python3 main.py
    File "main.py", line 30
      if addr == 0x68:
  SyntaxError: invalid syntax
WHAT HAPPENED
  The script died instantly with a parse error on a line that looked perfectly fine in the editor.
WHY IT HAPPENED (root cause)
  The line was missing its trailing colon - the editor's syntax highlighting had not refreshed, so the mistake was invisible. E0009 | v1.0 | BIG | Found Day 2 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : ssh: connect to host 192.168.1.42 port 22: Connection refused
Terminal  : Pi SSH terminal
  $ ssh pi@192.168.1.42
  ssh: connect to host 192.168.1.42 port 22: Connection refused
  $ ping 192.168.1.42
  64 bytes from 192.168.1.42: icmp_seq=1 ttl=64 time=2.1 ms
WHAT HAPPENED
  The morning started with an unreachable robot. Ping worked - the Pi was alive on the network - but SSH refused every connection.
WHY IT HAPPENED (root cause)
  After an unclean power cut, sshd never started. The machine booted into a degraded state: networking came up, but the ssh service was disabled by the failed boot sequence. Ping (ICMP) and SSH (TCP) are completely separate paths - the Pi was reachable at layer 3 while nothing listened on port 22 at layer 4. The symptom was 'robot unreachable' but the diagnosis needed to split the network stack into layers.
INVESTIGATION (before the fix)
  - Checked ping first to separate link failure from service failure
  - Checked `systemctl status ssh` - service was dead, not starting
  - Connected via the HDMI console to start sshd manually
FIX (took 2 days)
  Fixed by enabling ssh at boot (systemctl enable ssh) and adding a journald check to the morning script so a dead sshd is visible within seconds.

E0010 | v1.0 | BIG | Found Day 2 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : Permission denied (publickey,password)
Terminal  : Pi SSH terminal
  $ ssh pi@raspberrypi
  pi@raspberrypi: Permission denied (publickey,password).
  pi@raspberrypi's password:
  Permission denied, please try again.
WHAT HAPPENED
  SSH reached the Pi and asked for credentials, then rejected everything. The password that worked last week was suddenly wrong.
WHY IT HAPPENED (root cause)
  The default raspberry password had been changed at some point, and the new one was never recorded. SSH tries publickey first, then password; with no key installed and the wrong password, all attempts failed. The security hardening done 'to be safe' had become a brick wall because the credential was lost - a process problem, not a technical one.
INVESTIGATION (before the fix)
  - Tried the recorded password variants - all rejected
  - Tested if the Pi accepted keys - no key installed
  - Used the HDMI console to reset the password via sudo passwd
FIX (took 3 days)
  Fixed by resetting the password, installing an SSH key, and writing the credentials into the project notes so a lost password can never block the robot again.

E0011 | v1.0 | BIG | Found Day 2 | Fixed in 4 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED
Terminal  : Pi SSH terminal
  $ ssh pi@raspberrypi
  WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
  IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
  Host key verification failed.
WHAT HAPPENED
  SSH refused to connect with a security warning. The message was dramatic - 'SOMEONE IS DOING SOMETHING NASTY' - but the cause was mundane.
WHY IT HAPPENED (root cause)
  The SD card had been reflashed, which generates a new SSH host key. The PC's known_hosts file still held the old key, and SSH treats any mismatch as a possible man-in-the-middle attack. The warning is the security system working exactly as designed; the false alarm came from an undeclared reflash. Every reflash invalidates the trust record silently.
INVESTIGATION (before the fix)
  - Confirmed the Pi was reimaged (the only legit cause)
  - Checked the new key fingerprint against the console
  - Removed the stale entry from known_hosts
FIX (took 4 days)
  Fixed by running ssh-keygen -R raspberrypi to forget the old key, and adding a documented procedure that every reflash updates the key on all laptops.

E0012 | v1.0 | BIG | Found Day 2 | Fixed in 5 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v1.0/main.py
Error     : Kernel panic - not syncing: VFS: Unable to mount root fs
Terminal  : Pi SSH terminal
  [ 17.388465] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)
  [ 17.389002] Rebooting in 5 seconds..
  ... (loop)
WHAT HAPPENED
  The Pi refused to boot, looped for ten minutes, and showed a kernel panic on the console. The robot was dead at the start of the day.
WHY IT HAPPENED (root cause)
  An unclean power cut corrupted the SD card's filesystem. The kernel could not mount the root partition (VFS mount failure), panicked, and rebooted into the same failure. SD cards are the most fragile component in the robot: a power drop during a write can corrupt the FAT/ext4 structures, and there is no built-in recovery. The boot loop is the kernel's only response to an unmountable root.
INVESTIGATION (before the fix)
  - Watched the boot loop on the HDMI console to confirm it was a mount failure
  - Mounted the SD card on a PC to check the filesystem
  - Verified the card was physically intact with fsck
FIX (took 5 days)
  Fixed by reflashing the SD card from the backup image, and later hardening the robot with a UPS so power cuts can never corrupt the filesystem again.
