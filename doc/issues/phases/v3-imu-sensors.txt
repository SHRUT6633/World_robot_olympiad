E0001 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/log_imu.py
Error     : ToF distance frozen at 0
Terminal  : ESP32 serial monitor
  $ python3 log_imu.py
  dist: 0, 0, 0, 0, 0 mm
  wall state: UNKNOWN
WHAT HAPPENED
  The distance sensor returned exactly zero on every read. Not an error, not a range value - a perfect, suspicious zero every time.
WHY IT HAPPENED (root cause)
  The VL53L0X boot sequence requires specific register writes with strict timing between them. The init code skipped a required 5ms delay, so the sensor never left its boot state and returned the default register value of 0. The sensor was not broken - it was never initialized. This is why vendor init sequences must be copied exactly, including every delay.
FIX (took 1 day)
  Fixed by restoring the complete init sequence with all inter-register delays, and adding a power-on self-check that verifies a non-zero reading.

E0002 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : ToF range error 7 (VL53L1X) floods the log
Terminal  : ESP32 serial monitor
  $ python3 mpu6050_regs.py
  WARNING: range status 7 (signal fail)
  WARNING: range status 7 (signal fail)
  ... 600 lines/second ...
WHAT HAPPENED
  The console became a waterfall of identical warnings. Within seconds the useful log was buried under thousands of identical lines.
WHY IT HAPPENED (root cause)
  The reflective venue tile produced a weak return echo, so the VL53L1X reported range status 7 (signal fail). The error path logged at full loop rate with no throttle - 600 lines per second is simply the loop rate. Logging is I/O, and I/O at that rate saturated the serial link and starved the control loop of CPU time.
FIX (took 1 day)
  Fixed with a rate limiter that logs the error at most once per 2 seconds and counts the suppressed occurrences, mirroring the I2C fix.

E0003 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/log_imu.py
Error     : Wall state flips every frame
Terminal  : ESP32 serial monitor
  $ python3 log_imu.py
  state: LEFT WALL, RIGHT WALL, LEFT WALL, ...
  distance jitter +-4cm
WHAT HAPPENED
  The wall-following state changed sides every single frame, making the robot oscillate between two behaviors at 10Hz. The distance was stable within a few centimeters.
WHY IT HAPPENED (root cause)
  The state threshold sat exactly in the middle of the sensor's noise band. A 4cm jitter crossed the threshold in both directions constantly, and the state machine had no hysteresis - no memory of the previous state to suppress rapid toggling. Threshold logic without hysteresis amplifies sensor noise into state oscillation.
FIX (took 1 day)
  Fixed by adding a 6cm hysteresis band around the threshold so the state only changes when the distance clearly leaves the current side.

E0004 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : Camera capture returns a black frame
Terminal  : ESP32 serial monitor
  $ python3 mpu6050_regs.py
  frame mean = 2.1 (near black)
  camera seems dead
WHAT HAPPENED
  The camera test produced almost entirely black frames. The sensor was alive - the log showed it was capturing - but the image was dark.
WHY IT HAPPENED (root cause)
  The camera was still in preview mode with auto-exposure running when the first capture happened. The capture raced the exposure settling, so the frame froze before the sensor adapted to the light. A camera is not instantly ready: after start, the auto-exposure algorithm needs several frames to converge, and a read immediately after init captures the un-converged state.
FIX (took 1 day)
  Fixed by forcing a 500ms settle delay after camera start and discarding the first three frames before using any image.

E0005 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/log_imu.py
Error     : MPU6050 WHO_AM_I mismatch 0x00
Terminal  : ESP32 serial monitor
  $ python3 log_imu.py
  WHO_AM_I = 0x00 (expected 0x68)
  IMU not found on bus
WHAT HAPPENED
  The IMU log script reported the sensor was absent even though it was wired and powered. The address check failed on the very first register read.
WHY IT HAPPENED (root cause)
  The MPU6050 answers at 0x68 or 0x69 depending on the AD0 pin. With AD0 floating, the pin read as high at power-up and the chip moved to 0x69, while the code only probed 0x68. WHO_AM_I returning 0x00 means the device never even acknowledged - the wrong address was being addressed, so the chip stayed silent.
FIX (took 1 day)
  Fixed by pulling AD0 to ground with a resistor and adding a bus scan that discovers the device address instead of assuming it.

E0006 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : Calibration JSON has no 'gyro_offset' key
Terminal  : ESP32 serial monitor
  $ python3 mpu6050_regs.py
  KeyError: 'gyro_offset'
    File "mpu6050_regs.py", line 27, in load_calib
WHAT HAPPENED
  The IMU driver crashed at startup reading its calibration file. The file existed and looked complete - the schema was the problem.
WHY IT HAPPENED (root cause)
  The calibration file was produced by an older calibration script that stored the fields under different names. The loader used strict key access (calib['gyro_offset']) so a renamed key raised KeyError instantly. There was no schema version in the file and no migration path, so old and new files were indistinguishable until load time.
FIX (took 1 day)
  Fixed by adding a schema version field, a default fallback for missing keys, and regenerating imu_calib.json with the new format.

E0007 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/log_imu.py
Error     : Complementary filter alpha out of bounds
Terminal  : ESP32 serial monitor
  $ python3 log_imu.py
  filter_config.json: alpha=1.7
  pitch follows raw accel with spikes
WHAT HAPPENED
  The live pitch plot showed violent spikes as if the gyro was ignored. The filter ran, but the numbers made no physical sense.
WHY IT HAPPENED (root cause)
  The complementary filter weights gyro integration by alpha and the accelerometer by (1 - alpha). With alpha=1.7 the accelerometer weight became -0.7, so the filter was actively amplifying accelerometer noise instead of suppressing it. A typo in filter_config.json wrote 1.7 instead of 0.7, and nothing validated the config against the [0,1] domain the math requires.
FIX (took 1 day)
  Fixed by clamping alpha at load time and adding a config validator that rejects values outside [0,1] with a readable error.

E0008 | v3.0 | SMALL | Found Day 41 | Fixed in 1 day | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : Magnetometer saturates near the drive motors
Terminal  : ESP32 serial monitor
  $ python3 mpu6050_regs.py
  mag: x=+32767 y=-32767 z=+1024
  heading: jumping 0..359
WHAT HAPPENED
  The heading readout became random noise whenever the throttle rose. At standstill it was fine; the moment the motors spun, the compass went mad.
WHY IT HAPPENED (root cause)
  The QMC5883L's ADC saturated at its ±32767 output limits, which means the magnetic field at the sensor exceeded its measurement range. The motor current creates a strong magnetic field a few centimeters away, and at 2cm distance the field strength is comparable to the Earth's field the sensor is trying to measure. Saturated ADC values are not noise - they are clipped, which corrupts the heading completely.
FIX (took 1 day)
  Fixed by moving the sensor 5cm from the motor wiring, adding hard-iron offset calibration, and masking the heading while the throttle exceeds a threshold.

E0009 | v3.0 | BIG | Found Day 42 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v3.0/log_imu.py
Error     : All ToF sensors report 8190mm (max range)
Terminal  : Pi SSH terminal
  left: 8190  front: 8190  right: 8190
  wall state: OPEN everywhere
WHAT HAPPENED
  Every distance sensor reported exactly 8190mm - the maximum value of the VL53L0X. The robot believed the world was empty.
WHY IT HAPPENED (root cause)
  The VL53L0X API returns 8190mm as the 'no valid reading' sentinel, and the read path had never called the init function. Reads on an uninitialized sensor return the default maximum, which looks like a plausible distance. Three sensors agreeing on 8190 was the clue: real measurements never agree perfectly, but a sentinel value is identical everywhere. The code confused 'no reading' with 'far away'.
INVESTIGATION (before the fix)
  - Spotted all three sensors at the exact same value - impossible for real data
  - Checked the init call path - it was missing entirely
  - Verified the vendor example shows the init requirement
FIX (took 2 days)
  Fixed by adding the missing init call and treating 8190 as 'no reading' in the fusion layer instead of a distance.

E0010 | v3.0 | BIG | Found Day 42 | Fixed in 3 days | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : VL53L1X range status 4 (out of bounds) constant
Terminal  : ESP32 serial monitor
  status: 4  status: 4  status: 4
  distance frozen at 100mm
WHAT HAPPENED
  The front ToF froze at 100mm - exactly the minimum range of the sensor. The status code said 'out of bounds' on every read.
WHY IT HAPPENED (root cause)
  The glossy track surface produced a false early echo: the light pulse bounced back strongly from the surface itself, so the sensor believed a target was at its minimum range. Range status 4 is the sensor telling the truth about what it saw. Glossy surfaces are a known optical failure for time-of-flight sensors because the peak detection picks the wrong echo.
INVESTIGATION (before the fix)
  - Tested the same sensor against a matte target - read correctly
  - Compared status codes across surfaces
  - Confirmed the frozen value matched the sensor's minimum range
FIX (took 3 days)
  Fixed by switching to long-range mode with the peak detection tuned for low-reflectivity targets, and adding a status-code check that discards status 4 reads.

Error     : sensor_health flags all sensors dead on boot
Terminal  : Pi SSH terminal
  sensor 1: DEAD  sensor 2: DEAD  sensor 3: DEAD
  but all read fine 2 minutes later
WHAT HAPPENED
  The health monitor declared every sensor dead at boot, then two minutes later all of them read fine. The alarm was real - but the verdict was premature.

FIX (took 4 days)

E0012 | v3.0 | BIG | Found Day 42 | Fixed in 5 days | ESP32 serial monitor
----------------------------------------------------------------------
File      : history/v3.0/mpu6050_regs.py
Error     : MPU6050 FIFO overflows after 30s
Terminal  : ESP32 serial monitor
  E (30000) mpu6050: FIFO overflow (2048 bytes)
  gyro data: stale frames
WHAT HAPPENED
  Every 30 seconds the gyro stream glitched. The FIFO overflow error appeared exactly at the 30-second mark, every run, like clockwork.
WHY IT HAPPENED (root cause)
  The MPU6050 buffers samples in an internal 2048-byte FIFO, and the reader drained it at 50Hz while the sensor produced at 100Hz. The drain rate was half the fill rate, so the FIFO filled exactly at the overflow point - 30 seconds at these rates. The periodic glitch was the FIFO resetting, and the periodic timing was the giveaway: a hardware error would not repeat on a precise schedule.
INVESTIGATION (before the fix)
  - Noticed the glitch was perfectly periodic - rate mismatch, not hardware
  - Computed fill vs drain rates from the registers
  - Confirmed the FIFO level grew linearly between overflows
FIX (took 5 days)
  Fixed by draining the FIFO at 200Hz (twice the sensor rate) and monitoring the FIFO level register as a health metric.

E0024 | v3.1 | BIG | Found Day 44 | Fixed in 5 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v3.1/imu_calib.json
Error     : IMU calibration accepted garbage data
Terminal  : Pi SSH terminal
  $ python3 calibrate_imu.py
  collecting... done (120 samples)
  gyro bias: 1.34 deg/s (was 0.01)
  result: worse than before
WHAT HAPPENED
  The calibration tool ran 'successfully' but produced a bias 100x worse than the previous value. The tool had no way to know the robot was being bumped while it collected.
WHY IT HAPPENED (root cause)
  Calibration is a statistical estimate: it averages samples to find the bias. If the robot moves during collection, the samples contain real motion plus bias, and the average is corrupted. The tool trusted its input completely - it never checked whether the sensor was still, because stillness was an assumption, not a measurement. Garbage in, garbage out, with a success message on top.
INVESTIGATION (before the fix)
  - Re-ran the calibration with the robot untouched - bias returned to 0.01
  - Compared the sample variance between the two runs
  - Found the bump event in the session log by timestamp
FIX (took 5 days)
  Fixed by computing the sample variance before accepting the result and requiring the robot to be still, with a 'movement detected' warning when the variance is too high.

  The calibration tool ran 'successfully' but produced a bias 100x worse than the previous value. The tool had no way to know the robot was being bumped while it collected.
WHY IT HAPPENED (root cause)

  - Compared the sample variance between the two runs
  - Found the bump event in the session log by timestamp
