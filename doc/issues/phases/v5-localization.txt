E0001 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : np.linalg.LinAlgError: Singular matrix
Terminal  : systemd journal
  $ python3 dead_reckon.py
    File "dead_reckon.py", line 92, in update
      K = P @ H @ inv(S)
  np.linalg.LinAlgError: Singular matrix
WHAT HAPPENED
  The UKF crashed on its first update with all sensors dead. The innovation covariance was singular - the filter had no information at all.
WHY IT HAPPENED (root cause)
  With every sensor returning zero, the innovation covariance S became singular (determinant zero), and matrix inversion is undefined for singular matrices. The UKF assumes measurements carry some information; all-zero measurements violate that assumption. Mathematically this is the filter asking for the inverse of a zero matrix - the error is the correct behavior of the math, and the bug is that nothing prevented it.
FIX (took 1 day)
  Fixed by checking the condition number of S before the update and skipping the update when it exceeds a threshold, keeping the prediction only.

E0002 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : NaN appears in the covariance matrix
Terminal  : systemd journal
  $ python3 motion_tracker.py
  P = [[nan nan],[nan nan]]
  pose estimate frozen
WHAT HAPPENED
  The covariance matrix filled with NaN and the pose stopped updating. The filter neither crashed nor recovered - it just froze.
WHY IT HAPPENED (root cause)
  One corrupted measurement (a 0 divided during normalization) introduced NaN into the state, and every subsequent update propagated it through the linear algebra. The UKF has no built-in NaN detection; NaN arithmetic silently poisons every matrix product. The failure showed up minutes later as a frozen pose, long after the bad sample was long gone.
FIX (took 1 day)
  Fixed by validating every measurement with np.isfinite() before the update and rejecting non-finite samples with a logged warning.

E0003 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : Negative variance in the dead reckoning
Terminal  : systemd journal
  $ python3 dead_reckon.py
  variance: -0.004
  sigma = nan
WHAT HAPPENED
  The dead-reckoning output contained a negative variance, and the standard deviation computed from it became NaN. The motion estimate was mathematically impossible.
WHY IT HAPPENED (root cause)
  The noise model added a negative correction term after a wheel-slip event - slip reduces the estimated speed, and the speed-dependent noise formula produced a negative variance. Variance is defined as the expected squared deviation, which cannot be negative; the formula was wrong for the slip regime. Negative variance then breaks the sqrt used for the 1-sigma bound.
FIX (took 1 day)
  Fixed by clamping the variance to a minimum of 1e-6 and adding an assertion in tests that the variance never leaves the valid domain.

E0004 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : Outlier rejection drops 100% of measurements
Terminal  : systemd journal
  $ python3 motion_tracker.py
  accepted: 0/48 measurements
  pose drifts with no updates
WHAT HAPPENED
  The filter never updated - every single measurement was rejected as an outlier. The robot moved, but the pose estimate just drifted open-loop.
WHY IT HAPPENED (root cause)
  The Mahalanobis gate used chi-square threshold 3 (about 1 sigma) for a measurement that legitimately carries 2-3 sigma noise. With the gate set tighter than the noise, every genuine reading exceeded the threshold and was discarded. Outlier rejection assumes the model matches the noise; a gate calibrated for a different sensor or surface rejects the true signal as noise.
FIX (took 1 day)
  Fixed by raising the gate to chi-square 9 (3 sigma), then validating with the outlier_test that at least 95% of genuine measurements pass.

E0005 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : UKF alpha/beta/kappa parameter typo
Terminal  : systemd journal
  $ python3 dead_reckon.py
  ukf_params.json: alpha=1e-3 beta=2 kappa=1
  filter diverges on the first turn
WHAT HAPPENED
  The UKF diverged instantly on the first corner. The same data worked with the old parameters, so the filter itself was fine - the tuning was not.
WHY IT HAPPENED (root cause)
  The sigma-point spread parameter alpha controls how far the sigma points lie from the mean. alpha=1e-3 collapsed the sigma points almost onto the mean, so the filter's covariance estimate was tiny and it over-trusted its state. On the first turn the innovation was huge relative to that shrunken covariance, and the correction pulled the state wildly off. One digit in a JSON file changed the filter's behavior completely.
FIX (took 1 day)
  Fixed by restoring alpha=1e-2 from the tuning run and adding a startup check that alpha is within the valid (0,1] range.

E0006 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : Mag heading jumps 180 degrees on reversal
Terminal  : systemd journal
  $ python3 motion_tracker.py
  heading: 45 -> 225 (robot didn't turn)
  hard-iron offset missing
WHAT HAPPENED
  The heading readout flipped by exactly 180 degrees whenever the robot reversed direction. The robot never turned, but the compass said it had.
WHY IT HAPPENED (root cause)
  The hard-iron offset (the fixed magnetic distortion from the battery and wiring) was only applied in forward direction code paths. When reversing, the un-compensated raw vector rotated the heading by the offset magnitude - which here was almost exactly 180 degrees. The magnetometer measures the sum of the Earth field plus the constant distortion; without subtracting the distortion the heading formula is wrong.
FIX (took 1 day)
  Fixed by applying the calibrated hard-iron offset in both directions and adding the reverse path to the heading test cases.

E0007 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : Cross-verify reports 40cm disagreement
Terminal  : systemd journal
  $ python3 dead_reckon.py
  tof=0.82m  camera=0.42m  diff=0.40m
  camera scale wrong
WHAT HAPPENED
  The ToF and camera distance estimates disagreed by 40cm on the same target. One of them was right; the cross-verify test existed precisely to find which.
WHY IT HAPPENED (root cause)
  The camera distance scale was calibrated at 640x480, but the pipeline ran at 1280x720. The focal length in pixels doubles with resolution, so a scale factor valid at one resolution is wrong at the other. The two systems measured correctly in their own frames - the bug was a unit mismatch between the calibration domain and the runtime domain.
FIX (took 1 day)
  Fixed by re-running tof_camera_calib.py at the runtime resolution and storing the resolution in the calibration file so the scale can be validated at load.

E0008 | v5.0 | SMALL | Found Day 81 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : EKF linearization fails on sharp turns
Terminal  : systemd journal
  $ python3 motion_tracker.py
  ekf error: Jacobian is zero
  state: x=0.5 y=2.1 theta=nan
WHAT HAPPENED
  The EKF produced NaN heading on sharp turns. The filter worked on gentle curves and fell apart on the aggressive ones.
WHY IT HAPPENED (root cause)
  The EKF linearizes the motion model with a Jacobian evaluated at the current state. For a sharp turn the yaw Jacobian term was dropped in the model, so the Jacobian row became zero and the state transition lost its heading information - the estimate collapsed to NaN. The EKF's approximation quality depends on the Jacobian being accurate; a model simplified for straight driving is invalid at large steering angles.
FIX (took 1 day)
  Fixed by adding the missing yaw-dynamics term to the Jacobian and extending the ekf_test with a sharp-turn scenario.

E0009 | v5.0 | BIG | Found Day 82 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : UKF diverges and the robot drives off the track
Terminal  : Pi SSH terminal
  ukf: x=3.2 y=8.9 theta=2.1
  actual: x=1.8 y=2.0 theta=0.0
  UKF diverged, EKF fallback used
WHAT HAPPENED
  The robot drove off the track because the UKF believed the robot was somewhere else entirely. The pose was confident, detailed - and completely wrong.
WHY IT HAPPENED (root cause)
  The adaptive noise module grew the process noise with each suspicious measurement, and the filter's confidence in the state shrank with it. With enough noise inflation the filter trusted every new measurement blindly, and a single bad sensor reading dragged the pose far from reality. The adaptive mechanism had no upper bound on the noise it would tolerate - it adapted itself into failure.
INVESTIGATION (before the fix)
  - Plotted the UKF pose against the known track - divergence was gradual
  - Tracked the process noise growth over the run
  - Bounded the noise growth and re-ran - divergence gone
FIX (took 2 days)
  Fixed by bounding the adaptive noise growth to a maximum factor, and by adding a sanity gate that falls back to the EKF when the UKF and EKF disagree by more than 1m.

E0010 | v5.0 | BIG | Found Day 82 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : Dead reckoning drifts 30cm per lap
Terminal  : Pi SSH terminal
  dead reckoning: -0.30m off after 1 lap
  wheel slip on the carpet
WHAT HAPPENED
  The dead-reckoned position was 30cm off after every lap. The error was consistent, which made it diagnosable - and unavoidable without external reference.
WHY IT HAPPENED (root cause)
  Odometry assumes the wheels roll without slipping, but the carpet caused a consistent 3% slip that odometry cannot measure - it only counts rotations. Over a 10m lap, 3% is exactly 30cm. Pure dead reckoning has no way to know about slip because the encoder counts the same whether the wheel grips or slides; the model was perfect, the assumption was wrong.
INVESTIGATION (before the fix)
  - Measured the error over several laps - constant at 30cm
  - Computed the implied slip percentage - 3%, consistent
  - Fused the ToF wall distance as a lateral reference
FIX (took 3 days)
  Fixed by fusing the ToF wall distance into the lateral state, so the drift is corrected by an absolute reference instead of a second integration.

E0011 | v5.0 | BIG | Found Day 82 | Fixed in 4 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v5.0/dead_reckon.py
Error     : EKF position jumps 40cm at the first corner
Terminal  : Pi SSH terminal
  position: (1.2, 2.0) -> (1.6, 2.0) in one step
  measurement noise too small
WHAT HAPPENED
  At the first corner the EKF position jumped 40cm in a single update. The jump was instant - the filter re-trusted a single measurement over its own model.
WHY IT HAPPENED (root cause)
  The measurement noise matrix was tuned too optimistically: the filter believed the ToF more than the motion model. At the corner, one noisy reading passed the gate and the filter snapped to it. The EKF's estimate is a weighted compromise; the weights live in the noise matrices, so a too-small R matrix means 'trust the sensor blindly'.
INVESTIGATION (before the fix)
  - Logged the innovation at the corner - it was 10x the modeled noise
  - Tuned R against real logged data instead of guesses
  - Verified the jump disappeared with the realistic R
FIX (took 4 days)
  Fixed by tuning the measurement noise matrix from actual logged data (Allan variance for the sensors), and by gating the correction when the innovation exceeds 5 sigma.

E0012 | v5.0 | BIG | Found Day 82 | Fixed in 5 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v5.0/motion_tracker.py
Error     : Pose pipeline slows to 8Hz under load
Terminal  : Pi SSH terminal
  pipeline rate: 100Hz -> 8Hz
  CPU at 96% (vision + fusion)
WHAT HAPPENED
  The pose pipeline collapsed from 100Hz to 8Hz when the vision stack ran at full load. The robot's control degraded with it, because control depends on fresh pose data.
WHY IT HAPPENED (root cause)
  Vision and fusion ran in a single thread, and vision processing took 120ms per frame under load. The GIL serialized the Python work, so fusion starved behind vision. The architecture had no isolation between a 30fps vision workload and a 100Hz fusion workload - one process, one thread, one bottleneck.
INVESTIGATION (before the fix)
  - Measured the per-stage latency to find the bottleneck
  - Confirmed vision occupied the CPU while fusion waited
  - Split fusion into a separate process - rate recovered
FIX (took 5 days)
  Fixed by moving fusion to its own process with a shared-memory pose buffer, so a vision slowdown can no longer block control.
