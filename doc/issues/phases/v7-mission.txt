E0001 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : Parking overshoots the zone by 10cm
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  final offset: 0.10m  (limit 0.05m)
  partial points only
WHAT HAPPENED
  The parking maneuver stopped 10cm outside the zone - double the allowed tolerance. The robot lost 8 points to the overshoot.
WHY IT HAPPENED (root cause)
  The final correction used the same approach speed as the main run, and the correction controller could not react before the robot rolled through the boundary. Parking corrections operate in millimeters and need low speeds; at the run speed the controller latency alone consumed the tolerance. The speed schedule was one value for all phases, and the parking phase needed a different one.
FIX (took 1 day)
  Fixed by switching to CRAB_WALK for the last 10cm and capping the park approach speed at 0.15 m/s, with the tolerance margin verified in the park_sm test.

E0002 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Checkpoint is missed on the fast lap
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  checkpoint 2: MISSED
  shortcut not detected at speed
WHAT HAPPENED
  The robot passed through checkpoint 2 at speed and the system never noticed. On slow laps the checkpoint always registered - the miss was speed-dependent.
WHY IT HAPPENED (root cause)
  The checkpoint gate was checked at 10Hz, and at 2m/s the robot crossed the gate in 60ms - faster than the check period. The checker literally never observed the crossing; the event happened between samples. Periodic sampling can only detect events that last longer than the sample period.
FIX (took 1 day)
  Fixed by checking the gate every frame instead of every 100ms, and adding a position interpolation that detects gate crossings between frames.

E0003 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : Race strategy picks the slow lane
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  lane: outer (inner was free)
  lost 0.8s per lap
WHAT HAPPENED
  The race strategy chose the outer lane while the inner lane was clear, losing 0.8 seconds per lap. The choice was stable and consistent - and consistently wrong.
WHY IT HAPPENED (root cause)
  The lane score was computed once before the race and considered only static geometry. The inner lane's obstacle was gone by lap 2, but the score still penalized it. A decision based on stale information is not a strategy error - it is an information freshness error. The strategy answered the question 'which lane was best 2 minutes ago'.
FIX (took 1 day)
  Fixed by recomputing the lane score every lap from the live obstacle state, and logging the score so a wrong choice is visible in the log.

E0004 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Reverse logic oscillates at the obstacle
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  forward reverse forward reverse ...
  robot stuck for 4s
WHAT HAPPENED
  The robot shuffled forward and backward in front of an obstacle for four seconds. Both directions were correct decisions - in isolation.
WHY IT HAPPENED (root cause)
  The obstacle strategy evaluated the escape direction every frame, and each frame the evaluation flipped: after reversing a bit, the sensor saw a path forward again, and vice versa. A controller without state memory will oscillate whenever the sensor feedback lags the actuator. The hysteresis that exists in wall-following was missing here.
FIX (took 1 day)
  Fixed by adding a minimum dwell time in each direction state (0.5s), so the strategy commits to a direction instead of re-deciding every frame.

E0005 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : State machine stuck in IDLE
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  state: IDLE (30s)
  start line never detected
WHAT HAPPENED
  The robot sat at the start line for 30 seconds and never launched. The start detector was reporting, but the state machine was not listening.
WHY IT HAPPENED (root cause)
  The state machine waited for an event named 'start_detected', but the start detector published 'start_found'. Two modules used different names for the same fact - a vocabulary mismatch, not a logic error. Event-driven systems fail silently when events are named inconsistently, because the missing event simply never arrives.
FIX (took 1 day)
  Fixed by aligning the event names through a shared event constants module, and adding a startup check that logs the events each task publishes.

E0006 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Lap counter double counts a lap
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  laps: 0 1 2 3 3 4 (double count at 3)
  race finished a lap early
WHAT HAPPENED
  The lap counter logged lap 3 twice, so the robot believed the race ended one lap early. The count went 3, 3 - two events for one crossing.
WHY IT HAPPENED (root cause)
  The lap line check ran on every frame while the robot was on the line, and every frame produced a lap event. There was no state to remember that the line had already been crossed. A threshold crossing is a single event, but a per-frame comparison produces one event per frame - the missing piece is edge detection, not counting.
FIX (took 1 day)
  Fixed by adding a crossed flag that only resets after the robot leaves the line, so one crossing produces exactly one event.

E0007 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : Start detected on camera noise
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  start: DETECTED (t=0.2s)
  robot launches before the judge signal
WHAT HAPPENED
  The robot launched 0.2 seconds after boot - before the judge's signal. A dark frame edge had matched the start pattern.
WHY IT HAPPENED (root cause)
  The start detector was a single-frame pattern match, and a single noisy frame can contain anything. With no confirmation requirement, one false match was enough to launch. Detection systems that decide from one sample have the error rate of one sample; the fix is statistical, not algorithmic - require agreement across time.
FIX (took 1 day)
  Fixed by requiring three consecutive confirmed frames (over 60ms) before launching, and rejecting the first 500ms of camera frames after start.

E0008 | v7.0 | SMALL | Found Day 121 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Direction is inverted after the first reverse
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  direction: forward (robot is reversing)
  pillar logic wrong side
WHAT HAPPENED
  After the first reverse maneuver the robot's direction state said FORWARD while it was physically reversing. All pillar logic that depended on direction was wrong from that moment.
WHY IT HAPPENED (root cause)
  The reverse command was executed by the motor layer, but the direction flag lived in a different module and was never updated when the reverse command ran. Two copies of the truth (the actual motion and the recorded state) diverged, and nothing enforced their consistency. The state was updated at the command level, not at the motion level where the truth exists.
FIX (took 1 day)
  Fixed by updating the direction flag inside the reverse state action, and adding an assertion that compares the flag against the motor layer's reported direction.

E0009 | v7.0 | BIG | Found Day 122 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : Race strategy bets everything on the wrong lane
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  lane chosen: outer (inner clear)
  lost 1.5s over the race
WHAT HAPPENED
  The race strategy committed to the outer lane for all three laps while the inner lane was clear from lap 2 on. A wrong early decision was locked in.
WHY IT HAPPENED (root cause)
  The lane decision was made once before lap 1 from a single observation. Track conditions change during a race - an obstacle may move or a line may clear - and a one-time decision cannot adapt. Committing to a fixed plan in a dynamic environment turns every change into a penalty.
INVESTIGATION (before the fix)
  - Replayed the race - the inner lane was clear from lap 2
  - Checked when the strategy re-evaluates - only at race start
  - Made the lane score re-evaluate at every lap boundary
FIX (took 2 days)
  Fixed by recomputing the lane score at every lap boundary, and by adding a mid-race override when the live obstacle state changes by more than a threshold.

E0010 | v7.0 | BIG | Found Day 122 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Checkpoint gate triggers twice per crossing
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  checkpoint 3: 2 events
  bonus counted twice
WHAT HAPPENED
  Every checkpoint produced two events instead of one, doubling the bonus count. The scoring was quietly wrong by a factor of two.
WHY IT HAPPENED (root cause)
  The gate trigger fired on both the leading edge and the trailing edge of the crossing - the code treated entering and leaving the gate as two separate events. A gate is a region, and the trigger logic did not define which transition counts. Without an explicit edge definition, every boundary transition is an event.
INVESTIGATION (before the fix)
  - Counted the events per crossing - exactly two, every time
  - Traced the trigger to both boundary transitions
  - Added a cleared-edge requirement and re-ran
FIX (took 3 days)
  Fixed by triggering only on entry and requiring the gate to be fully cleared before the next trigger, verified in the checkpoint test.

E0011 | v7.0 | BIG | Found Day 122 | Fixed in 4 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/test_state_machine.py
Error     : Reverse logic stalls at a wall
Terminal  : Pi SSH terminal
  $ python3 test_state_machine.py
  reverse: 0.2s, forward: 0.2s, loop
  robot stuck for 9s
WHAT HAPPENED
  The robot shuffled against a wall for nine seconds, reversing 0.2s and advancing 0.2s forever. Both motions worked; the combination was useless.
WHY IT HAPPENED (root cause)
  The reverse duration was a fixed 0.2 seconds, shorter than the time needed to clear the wall overlap. Each forward attempt re-engaged the wall by more than the reverse had cleared, so the net progress per cycle was negative. A fixed parameter can only be correct for one geometry; the wall overlap varies.
INVESTIGATION (before the fix)
  - Measured the wall overlap vs the reverse distance - negative net
  - Timed how long a reverse needed to clear the overlap
  - Made the reverse distance proportional to the overlap
FIX (took 4 days)
  Fixed by making the reverse distance proportional to the measured obstacle overlap, and adding a minimum total reverse time to the strategy.

E0012 | v7.0 | BIG | Found Day 122 | Fixed in 5 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v7.0/state_machine.py
Error     : Lap counter breaks when the robot stops on the line
Terminal  : Pi SSH terminal
  $ python3 state_machine.py
  laps: 2 (stopped exactly on the line)
  race cannot finish
WHAT HAPPENED
  The robot stopped exactly on the lap line and the counter refused to advance. The robot was on the line - why did the count not register?
WHY IT HAPPENED (root cause)
  The lap counter only counted a lap when it observed a transition from 'not on line' to 'on line'. The robot crossed the line while the counter was still resolving the previous state, so no transition was ever observed. Counting transitions instead of positions means a valid crossing can be invisible if it coincides with the state resolution.
INVESTIGATION (before the fix)
  - Reproduced by stopping exactly on the line
  - Checked the counter logic - it demanded a transition
  - Added a position-based check that accepts a stationary crossing
FIX (took 5 days)
  Fixed by also counting a lap when the robot is detected on the line in the correct direction while the previous lap is already confirmed.

  The robot shuffled forward and backward in front of an obstacle for four seconds. Both directions were correct decisions - in isolation.
