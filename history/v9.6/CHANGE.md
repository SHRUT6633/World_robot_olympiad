# v9.6 — Integration Test

## What Changed

Until v9.6, we had unit tests for individual modules (sensors, control, fusion) but no test that simulated a full race. Unit tests catch bugs in isolation, but they miss integration issues: the camera returns a frame but the perception module doesn't see pillars because the colour space conversion is wrong, or the UKF produces a pose but the localization module doesn't update because the `attach_filter()` call was missing, or the state machine never transitions because the lap counter resets on every tick.

I created `tests/integration/test_full_pipeline.py` which simulates a complete race lap using mocked hardware. The test:

1. Mocks all hardware drivers (camera, ToF, IMU, magnetometer, UART)
2. Creates a full SystemManager and registers all components (same as main.py)
3. Runs the scheduler for a simulated 30-second race
4. Feeds pre-recorded camera frames and sensor data from disk
5. Verifies that the state machine progresses through expected states: INIT -> IDLE -> FORWARD -> CORNERING -> OBSTACLE_AVOID -> ...
6. Verifies that the lap counter increments correctly
7. Verifies that UART commands are sent (mocked serial write calls checked)
8. Verifies that no components are marked "dead" by HealthMonitor
9. Verifies that the scheduler's stats are within expected bounds (no tasks with excessive jitter)

## Errors Encountered and Fixed

**Error 1: The test takes 5 minutes to run.**
The full race simulation runs at real-time speed because the camera frame reader was designed to stream from disk at 30 fps. Over 30 simulated seconds of race time, the test actually waits 30 real seconds. With setup, teardown, and multiple assertion checks, the total runtime was 5+ minutes.

Running a 5-minute test on every `git push` is impractical. Developers would stop running tests locally, and CI would take forever.

**Fix:** I marked the test with `@pytest.mark.slow`:
```python
@pytest.mark.slow
async def test_full_race_pipeline():
    ...
```

And configured `pytest` in `setup.cfg` to skip slow tests by default:
```ini
[tool:pytest]
testpaths = tests
markers =
    slow: marks tests as slow (skipped in CI by default)
addopts = -m "not slow"
```

CI runs `pytest -m "not slow"` (fast tests only). Developers can run `pytest -m slow` locally when they specifically want to test integration.

**Error 2: Mocked hardware doesn't reproduce real-world timing.**
The mocked camera returns frames instantly (no I2C delays, no buffer reads). This means the scheduler sees tasks completing much faster than in reality, giving a false sense of timing margin. The test passed with 0% jitter, but real hardware has 2-8 ms of jitter per task.

**Fix:** I added artificial delays to the mocked hardware using `asyncio.sleep()`:
```python
class MockCamera:
    async def read(self):
        await asyncio.sleep(0.005)  # Simulate 5ms I2C read
        return self.frames[self._idx]
```

This makes the test more realistic but also slower — one of the reasons it's `@pytest.mark.slow`.

**Error 3: Test data needs to be versioned.**
The pre-recorded camera frames and sensor data are 200+ MB of binary files. Committing them to the repository would bloat the repo (undoing the v9.5 cleanup).

**Fix:** I used a GitHub LFS track pattern for the test data, or alternatively, I put the test data generation in a separate script (`tests/integration/generate_test_data.py`) that creates synthetic frames and sensor readings. The script is small (~200 lines) and generates the data on first run. The test data directory is added to `.gitignore` and generated by CI when needed.

## Alternatives Considered

1. **Hardware-in-the-loop (HIL) testing.** I considered running the test on actual Raspberry Pi hardware connected to a simulator. This would be the most realistic test, but it's impractical for CI — GitHub Actions can't run Pi hardware.

2. **Unit-test-only strategy.** Some teams skip integration tests entirely and rely on well-factored unit tests. But we've been bitten by integration bugs before (the UKF/ localization mismatch in v7), so integration testing is essential.

3. **Subset simulation.** Instead of a full 30-second race, I could simulate just the first 5 seconds (init + pillar detection + first corner). This would be faster but wouldn't catch lap-counting or parking issues.
