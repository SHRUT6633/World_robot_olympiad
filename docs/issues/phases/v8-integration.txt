E0001 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : Task base double-schedules a callback
Terminal  : systemd journal
  $ python3 steer_same.py
  callback ran twice per tick
  motor command overwritten
WHAT HAPPENED
  Every control tick produced two motor commands, the second overwriting the first. The motion was erratic because half the commands were stale by one tick.
WHY IT HAPPENED (root cause)
  register_task was called twice for the same task ID in main - once by the module's own registration and once by the application wiring. The scheduler had no duplicate detection, so it added the callback twice. The scheduler trusted its caller; the caller did not check whether the task was already registered.
FIX (took 1 day)
  Fixed by guarding register_task with a task-ID set that rejects duplicates, and logging a warning when a duplicate registration is attempted.

E0002 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steering_common.py
Error     : Log severity mapping is wrong
Terminal  : systemd journal
  $ python3 steering_common.py
  ERROR logged as INFO
  failures hidden in the console
WHAT HAPPENED
  Critical failures appeared in the log with the INFO level, so nobody noticed them in the morning's flood of messages. The logging was lying about importance.
WHY IT HAPPENED (root cause)
  The severity enum in log_severity.py and the level table in the logger used different orderings, so the numeric codes mapped to the wrong levels. The logger wrote what it was told - the mapping was corrupted upstream. Two files defining the same concept independently is a maintenance trap: they will drift until someone notices.
FIX (took 1 day)
  Fixed by defining the severity enum in the logger module itself and importing it everywhere, so only one source of truth exists.

E0003 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : YAML parse error in default_config.yaml
Terminal  : systemd journal
  $ python3 steer_same.py
  yaml.scanner.ScannerError: mapping values are not allowed here
  config failed to load
WHAT HAPPENED
  The robot refused to boot because the configuration file could not be parsed. The file looked correct to a human - the colon in a string was the problem.
WHY IT HAPPENED (root cause)
  YAML treats an unquoted colon followed by a space as a key/value separator. A string containing 'mode: fast' inside a value breaks the parser because it sees a nested mapping where it did not expect one. YAML is whitespace- and punctuation-sensitive in ways that are invisible to a quick read, which is why config errors show up at load time, never at edit time.
FIX (took 1 day)
  Fixed by quoting the value, and adding a config validation step at boot that parses the YAML and reports the exact line of any syntax error.

E0004 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steering_common.py
Error     : Surprise rule key is unknown
Terminal  : systemd journal
  $ python3 steering_common.py
  KeyError: 'pillar_logic' in surprise_config
  rules ignored, defaults used
WHAT HAPPENED
  The surprise rules loaded without error, but the pillar logic rule never took effect - the robot ran the default behavior all day.
WHY IT HAPPENED (root cause)
  The loader read keys by an explicit allowlist, and 'pillar_logic' was not in it, so the rule was silently dropped. A missing key in a config lookup is a silent failure when the code uses .get() with a default and a crash when it uses [] - this code used a path that neither crashed nor worked. The rules file and the loader schema had drifted apart.
FIX (took 1 day)
  Fixed by adding the key to the loader schema and logging a warning whenever a configured rule key is ignored, so silent drops become visible.

E0005 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : Steering mode switch race condition
Terminal  : systemd journal
  $ python3 steer_same.py
  mode: OPPOSITE (expected CRAB)
  one-frame wrong steering at the switch
WHAT HAPPENED
  For exactly one frame at every mode switch, the robot steered with the wrong geometry. The switch itself worked - the frame in between did not.
WHY IT HAPPENED (root cause)
  The mode flag was written by the mission thread and read by the control thread without synchronization. The control thread could read the flag mid-update, observing a mixed state. A one-frame glitch is exactly what a data race looks like: mostly correct, occasionally wrong, impossible to reproduce on demand.
FIX (took 1 day)
  Fixed by making the mode switch atomic - the mode lives in a single int that the scheduler publishes, and the control thread reads it through a lock-free once-store.

E0006 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steering_common.py
Error     : Heartbeat times out on a busy CPU
Terminal  : systemd journal
  $ python3 steering_common.py
  heartbeat lost: 1500ms
  motors cut mid-run
WHAT HAPPENED
  The motors cut out for a moment in the middle of a run, then resumed. The failsafe fired, then recovered on its own - a glitch with consequences.
WHY IT HAPPENED (root cause)
  The heartbeat thread could not get CPU time during perception spikes, so the failsafe correctly concluded the main loop was dead and cut the motors. The failsafe is designed to be conservative: any doubt means stop. The bug was that a healthy but busy system looked dead to the heartbeat - the failure detector could not distinguish 'slow' from 'dead'.
FIX (took 1 day)
  Fixed by raising the heartbeat thread priority and extending the timeout to 2s, with a separate watchdog that only fires when the main loop is truly stuck.

E0007 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : Health monitor false alarm on sensor 3
Terminal  : systemd journal
  $ python3 steer_same.py
  sensor 3: FAIL (3 misses)
  actually fine, just slow
WHAT HAPPENED
  The health monitor declared the ToF dead at every boot. The sensor was alive - it was just slow to warm up, and the monitor did not wait.
WHY IT HAPPENED (root cause)
  The failure threshold was three consecutive misses, and the ToF's warm-up period legitimately produces more than three misses before its first valid reading. The threshold was calibrated against runtime behavior, not boot behavior. A monitor with a fixed threshold cannot distinguish a boot transient from a persistent failure.
FIX (took 1 day)
  Fixed by raising the threshold to 20 misses and adding a warm-up grace period of 5 seconds at boot, matching the measured sensor ready time.

E0008 | v8.0 | SMALL | Found Day 141 | Fixed in 1 day | systemd journal
----------------------------------------------------------------------
File      : history/v8.0/steering_common.py
Error     : Track map is off by one section
Terminal  : systemd journal
  $ python3 steering_common.py
  section: 5 (expected 4)
  strategy picks the wrong corner
WHAT HAPPENED
  Every lap the track map believed the robot was one section further along than reality. The strategy consistently prepared the wrong corner.
WHY IT HAPPENED (root cause)
  The section counter incremented on both entering and exiting the section boundary line, because the boundary check ran on the transition in both directions. A line crossing is a single event, but the code detected it twice - once entering, once leaving. The off-by-one was perfectly consistent, which made it look like a constant and masked it as a real offset.
FIX (took 1 day)
  Fixed by incrementing the section only on entry, and adding a test that drives the full lap and asserts the counter ends exactly at the section count.

E0009 | v8.0 | BIG | Found Day 142 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : OOM killer kills the perception process
Terminal  : Pi SSH terminal
  $ python3 steer_same.py
  Out of memory: Killed process 1234 (vision)
  perception dead, robot runs blind
WHAT HAPPENED
  The perception process was killed by the kernel's OOM killer mid-run. The robot kept driving - blind, because nobody noticed the process was gone.
WHY IT HAPPENED (root cause)
  The vision frame queue had no size limit, so under load it buffered frames without bound and consumed the Pi's RAM. When memory ran out, the kernel's OOM killer chose the largest process - the vision process. The queue was a convenience that became a memory leak the moment consumers lagged producers.
INVESTIGATION (before the fix)
  - Checked dmesg for the OOM kill - the vision process was the target
  - Measured the RSS growth - it grew linearly with queue length
  - Capped the queue and re-ran under load
FIX (took 2 days)
  Fixed by capping the frame queue at 4 frames with drop-oldest, and adding a memory watch that logs the RSS of each process to the health monitor.

E0010 | v8.0 | BIG | Found Day 142 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v8.0/steering_common.py
Error     : Log severity floods the disk on a bad day
Terminal  : Pi SSH terminal
  $ python3 steering_common.py
  /var/log: 4.2GB of WARNING lines
  SD card 99% full
WHAT HAPPENED
  One bad day of testing filled the SD card with 4.2GB of warning lines. The robot kept working - until the card was full and everything stopped.
WHY IT HAPPENED (root cause)
  A rate-limit regression let the error logger write at full rate, and the log had no rotation on the embedded system. Logging is storage I/O; unbounded logging is an unbounded disk consumption. The rate limiter that had fixed the console spam did not cover the file writer.
INVESTIGATION (before the fix)
  - Found the 4.2GB log and its growth rate
  - Traced the spam to a rate-limiter regression
  - Added rotation and a disk watermark alert
FIX (took 3 days)
  Fixed by fixing the rate limiter for the file writer and adding log rotation with a 50MB cap, plus a warning when the disk crosses 90%.

E0011 | v8.0 | BIG | Found Day 142 | Fixed in 4 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v8.0/steer_same.py
Error     : Scheduler deadlocks when a task raises
Terminal  : Pi SSH terminal
  $ python3 steer_same.py
  scheduler: task 'vision' raised, never resumed
  all other tasks stop
WHAT HAPPENED
  One exception in the vision task froze the entire robot - every other task stopped scheduling. The failure was in the exception path, not the task.
WHY IT HAPPENED (root cause)
  The scheduler loop had no exception boundary around its task invocations. When vision raised, the exception propagated out of the loop, and the asyncio gather never continued, so no task ever ran again. A system of cooperating tasks is only as robust as its weakest task unless the scheduler contains each one.
INVESTIGATION (before the fix)
  - Reproduced with a forced exception in a test task
  - Confirmed the gather exited and nothing resumed
  - Wrapped each task call in try/except and re-ran
FIX (took 4 days)
  Fixed by wrapping every task invocation in try/except with logging, so a failing task is isolated and the scheduler keeps running.

Error     : Steering mode switch race condition
Terminal  : VS Code terminal
  $ python3 task_base.py
  mode: OPPOSITE (expected CRAB)
  one-frame wrong steering at the switch
WHAT HAPPENED
  For exactly one frame at every mode switch, the robot steered with the wrong geometry. The switch itself worked - the frame in between did not.

Error     : Heartbeat times out on a busy CPU
Terminal  : VS Code terminal
  $ python3 scheduler.py
  heartbeat lost: 1500ms
  motors cut mid-run
WHAT HAPPENED
  The motors cut out for a moment in the middle of a run, then resumed. The failsafe fired, then recovered on its own - a glitch with consequences.
WHY IT HAPPENED (root cause)
  The heartbeat thread could not get CPU time during perception spikes, so the failsafe correctly concluded the main loop was dead and cut the motors. File      : history/v8.7/scheduler.py
Error     : ESP32 flash with the wrong partition table
Terminal  : Pi SSH terminal
  $ python3 scheduler.py
  esptool: data does not match the partition table
  ESP32 boot loops
WHAT HAPPENED
  After flashing, the ESP32 boot-looped. The flash succeeded - the app was written to a partition the partition table did not define.
WHY IT HAPPENED (root cause)
  The application partition had grown past the size declared in the partition table, or the table itself was for a different flash layout. The chip boots into the app region from the table; if the table does not describe the flashed layout, the bootloader cannot find the app and resets. The build and the flash layout were not validated against each other.

  - Compared the partition table with the app size
  - Reflashed with the standard 4MB table
FIX (took 2 days)
  Fixed by pinning the partition table in the project config, and adding a CI check that fails if the compiled app exceeds its partition.

E0094 | v8.7 | BIG | Found Day 156 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v8.7/task_base.py
Error     : OOM killer kills the perception process
Terminal  : Pi SSH terminal
  $ python3 task_base.py
  Out of memory: Killed process 1234 (vision)
  perception dead, robot runs blind
WHAT HAPPENED
  The perception process was killed by the kernel's OOM killer mid-run. The robot kept driving - blind, because nobody noticed the process was gone.
WHY IT HAPPENED (root cause)
  The vision frame queue had no size limit, so under load it buffered frames without bound and consumed the Pi's RAM. When memory ran out, the kernel's OOM killer chose the largest process - the vision process. The queue was a convenience that became a memory leak the moment consumers lagged producers.
INVESTIGATION (before the fix)
  - Checked dmesg for the OOM kill - the vision process was the target
  - Measured the RSS growth - it grew linearly with queue length
  - Capped the queue and re-ran under load
FIX (took 3 days)
  Fixed by capping the frame queue at 4 frames with drop-oldest, and adding a memory watch that logs the RSS of each process to the health monitor.

FIX (took 1 day)
  Fixed by raising the heartbeat thread priority and extending the timeout to 2s, with a separate watchdog that only fires when the main loop is truly stuck.
