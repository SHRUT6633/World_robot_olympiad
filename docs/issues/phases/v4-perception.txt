E0001 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : Lane offset jumps by a full lane width
Terminal  : Pi SSH terminal
  $ python3 config.py
  offset: 0.02 -> 0.47 (one frame)
  lane lost for 0.3s
WHAT HAPPENED
  The lane offset jumped from center to a full lane width away in a single frame. The steering twitched violently and then recovered.
WHY IT HAPPENED (root cause)
  When the line had a gap, the detector locked onto a neighboring line - the other lane's edge or a shadow - and reported it as the track line. The offset filter had no state, so one wrong frame was trusted completely for one control tick. Vision systems without temporal consistency treat every frame as a fresh truth, which amplifies single-frame errors.
FIX (took 1 day)
  Fixed by tracking the last-good line position and snapping back to it when the new detection is more than a lane-width away.

E0002 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : Camera resolution mismatch with calibration
Terminal  : Pi SSH terminal
  $ python3 lane_detect.py
  cv2.error: (-215:Assertion failed)
  !src.empty() in function 'undistort'
WHAT HAPPENED
  The camera pipeline crashed on undistort. The calibration data loaded fine, so the mismatch was invisible until the function call.
WHY IT HAPPENED (root cause)
  The camera opened at 1280x720 but the calibration was done at 640x480. cv2.undistort requires the image size to match the camera matrix, and the mismatch triggered OpenCV's internal assertion. The two settings lived in different config files that were never cross-checked - one for the camera driver, one for the calibration loader.
FIX (took 1 day)
  Fixed by forcing both to the same resolution in camera_config.py and adding a boot check that compares the frame size with the calibration size.

E0003 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : HSV lower bound bigger than upper bound
Terminal  : Pi SSH terminal
  $ python3 config.py
  ValueError: lower should be smaller than upper
    File "config.py", line 34, in detect
WHAT HAPPENED
  The red pillar detector crashed the first time it processed a real frame. The color range that worked in tests was rejected by OpenCV.
WHY IT HAPPENED (root cause)
  Red hue wraps around the HSV cylinder: red is both 0-10 and 170-180. Writing it as one continuous range (170..10) is invalid because lower > upper, which cv2.inRange rejects with a ValueError. The wrapper range is a conceptual mistake - the hue circle has no beginning, so the mask must be built from two disjoint ranges and OR-ed together.
FIX (took 1 day)
  Fixed by splitting the red range into two masks (0-10 and 170-180) and OR-ing the results, with a comment explaining the hue wrap.

E0004 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : ZeroDivisionError in distance estimate
Terminal  : Pi SSH terminal
  $ python3 lane_detect.py
    File "lane_detect.py", line 58, in estimate
      dist = known_h / h
  ZeroDivisionError: float division by zero
WHAT HAPPENED
  The pillar distance estimator crashed mid-frame, not at startup. The contour had been found, but its height was zero.
WHY IT HAPPENED (root cause)
  The detector found a contour but the color filter had removed every interior pixel, leaving a height of zero. The distance formula assumes a valid height; dividing by zero raised ZeroDivisionError. This is a data-quality failure: the pipeline did not validate its input before applying the pinhole model, so a degenerate contour crashed the math instead of being skipped.
FIX (took 1 day)
  Fixed by skipping contours smaller than 5 pixels and returning 'unknown' instead of crashing when the height is invalid.

E0005 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : Pillar detected at every frame edge
Terminal  : Pi SSH terminal
  $ python3 config.py
  pillar: (5, 20)  pillar: (610, 20)  ...
  false positives on the wall
WHAT HAPPENED
  The detector reported pillars at fixed screen positions in every frame. The track walls were being detected as red pillars.
WHY IT HAPPENED (root cause)
  The wall's edge pixels had similar HSV values to the pillar under the venue lighting, and the detector only matched color - it never checked size or shape. Any red-ish region, including a wall edge, passed the filter. A single-channel color test is necessary but not sufficient; without area and aspect-ratio constraints every similarly colored region is a candidate.
FIX (took 1 day)
  Fixed by adding a minimum area check and an aspect-ratio gate, and by masking the bottom 15% of the frame where the wall always appears.

E0006 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : Red and pink pillars are confused
Terminal  : Pi SSH terminal
  $ python3 lane_detect.py
  color=red  (was pink)
  confusion at hue 168-175
WHAT HAPPENED
  The color classifier called a pink pillar red. The two classes were defined by hue bands that overlapped, so the classification was ambiguous by construction.
WHY IT HAPPENED (root cause)
  Pink and red differ in saturation and lightness, not much in hue. The classifier only used hue, so any pixel in the overlapping 168-175 band was claimed by both classes. Classifying colors by a single channel cannot separate classes that are distinct in a different channel - the feature space was too small for the problem.
FIX (took 1 day)
  Fixed by narrowing the red band and adding a saturation threshold of 90, since pink has measurably lower saturation than the official red.

E0007 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : Free space is NaN after a corner
Terminal  : Pi SSH terminal
  $ python3 config.py
  free_space: nan
  corner left: nan
WHAT HAPPENED
  The free-space estimate became NaN at every corner. The robot continued driving, but the planner received garbage for the entire turn.
WHY IT HAPPENED (root cause)
  While angling through a corner, the ToF reported 0mm (out of range), and the fusion code divided by that reading to normalize the estimate. NaN is infectious: one 0/0 poisons every downstream calculation, and because NaN comparisons are all false, no safety check could catch it. The corner is exactly where the sensor points at a gap, so this happened on every lap.
FIX (took 1 day)
  Fixed by replacing non-finite values with the sensor's max range and adding a validation pass that rejects NaN before fusion.

E0008 | v4.0 | SMALL | Found Day 61 | Fixed in 1 day | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : Corner detection misses 180-degree turns
Terminal  : Pi SSH terminal
  $ python3 lane_detect.py
  corner count = 0 after full lap
  expected 4 corners
WHAT HAPPENED
  The lap trace showed zero corners even though the robot clearly turned four times. The detector only watched distance, and the hairpin was too smooth.
WHY IT HAPPENED (root cause)
  The corner detector used a distance-only signature: it watched the wall distance change. A 180-degree turn made with a wide arc changes distance slowly and smoothly, so the slope never exceeded the trigger threshold. The signature was chosen for right-angle corners, and a different geometry produced a different signature entirely - one feature cannot describe all corner shapes.
FIX (took 1 day)
  Fixed by adding the heading-change signature from the IMU, and requiring both signatures for a confirmed corner.

E0009 | v4.0 | BIG | Found Day 62 | Fixed in 2 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : Free space wrongly reports a corridor
Terminal  : Pi SSH terminal
  free space: 0.9m corridor detected
  reality: 0.4m gap
WHAT HAPPENED
  The free-space module reported a 0.9m corridor where only a 0.4m gap existed. The robot planned to drive through a space it could not fit through.
WHY IT HAPPENED (root cause)
  The fusion code averaged the ToF wall distance with the camera gap estimate. Averaging is only valid when both measurements describe the same quantity; here one sensor measured the wall and the other measured the gap, and the mean produced a number that matched neither reality. The 'corridor' was a pure artifact of mixing incompatible measurements.
INVESTIGATION (before the fix)
  - Reproduced the false corridor with the ToF and camera both active
  - Logged each sensor's raw value - they disagreed fundamentally
  - Tested taking the minimum instead of the mean - correct result
FIX (took 2 days)
  Fixed by taking the minimum of the two estimates (the conservative choice for a gap) and by storing the source of each free-space measurement.

E0010 | v4.0 | BIG | Found Day 62 | Fixed in 3 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : Pillar tracking loses the pillar at 2m/s
Terminal  : Pi SSH terminal
  tracked: 10 frames, lost at frame 11
  pillar reappears 20 frames later
WHAT HAPPENED
  The tracker followed the pillar perfectly at low speed, then lost it the moment the robot accelerated. It always lost it at the same point on the approach.
WHY IT HAPPENED (root cause)
  The tracker searched a fixed window around the last known position. At 2m/s the pillar moves several pixels between frames, and once it left the search window the tracker had nothing to lock onto. The search window size was tuned for walking speed, not race speed. A tracker with no motion model is only as fast as its window is wide.
INVESTIGATION (before the fix)
  - Measured the pillar's inter-frame displacement at speed
  - Found the displacement exceeded the search window
  - Predicted the position with odometry - tracking held
FIX (took 3 days)
  Fixed by predicting the search window center with the odometry velocity before matching, and widening the window proportional to speed.

E0011 | v4.0 | BIG | Found Day 62 | Fixed in 4 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/config.py
Error     : Pillar never detected under venue lights
Terminal  : Pi SSH terminal
  pillars: 0 found (12 frames)
  HSV test on the phone: 0 found
  color bands all wrong
WHAT HAPPENED
  The pillar detector found nothing for the entire morning. The same code had detected pillars perfectly in the lab the day before.
WHY IT HAPPENED (root cause)
  The morning sun changed the color temperature of the light, shifting every color's HSV values. Fixed HSV bands are calibrated for one lighting condition; a different light source moves the same physical color to a different point in HSV space. Vision systems are lighting-dependent by nature - the color of light is part of the measurement, not a nuisance term.
INVESTIGATION (before the fix)
  - Confirmed detection worked in the lab under fluorescent light
  - Sampled the pillar's HSV values under the morning sun
  - Compared the sampled values with the configured bands
FIX (took 4 days)
  Fixed by re-running the color calibration on the venue floor at the same time of day as the competition, and by making the calibration tool part of the morning routine.

E0012 | v4.0 | BIG | Found Day 62 | Fixed in 5 days | Pi SSH terminal
----------------------------------------------------------------------
File      : history/v4.0/lane_detect.py
Error     : Visual odometry scale explodes after a turn
Terminal  : Pi SSH terminal
  vo scale: 1.0 -> 9.3
  pose jumps 0.4m per frame
WHAT HAPPENED
  After the 90-degree turn, the visual odometry started reporting absurd distances - the pose jumped 0.4 meters per frame while the robot moved a few centimeters.
WHY IT HAPPENED (root cause)
  Visual odometry estimates motion from feature point displacement and derives the scale from the baseline between frames. After a sharp turn, feature matching lost the reference set and re-matched against a new baseline, and the scale estimate - unconstrained by any absolute reference - diverged. Monocular scale is only observable while the same features persist; a turn breaks that chain.
INVESTIGATION (before the fix)
  - Plotted the scale factor over time - flat before the turn, exploding after
  - Counted matched features across the turn - dropped below the threshold
  - Replayed the turn with forced re-initialization - problem vanished
FIX (took 5 days)
  Fixed by re-initializing the baseline when the matched feature count drops below 20, and by clamping the scale factor to a physically plausible range.
